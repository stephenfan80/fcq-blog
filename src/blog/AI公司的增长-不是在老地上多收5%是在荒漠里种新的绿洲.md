Lenny's Podcast 这期访谈，Anthropic 增长负责人 Amol Avisari 抛出了一个一开始听起来挺"老生常谈"的判断：如果你是一家 AI 优先的公司，应该把更多资源压到大赌注上，而不是按传统增长教科书那样跑小步快跑、hill climbing 的小优化。我刚听到这句话的时候没特别在意——这种"AI 时代要不一样思考"的话每周都能听三遍。但接下来他给的理由让我把进度条往回拉了一段：Anthropic 两年后能交付的产品价值，大约是今天的 100 到 1000 倍。前面还有大片大片完全没人占据的产品空间。这种时候，弹药应该花在"再种出一片新的绿洲"上，而不是花在"老地上能不能再多收 5%"上。他甚至举了个例子：Chrome 扩展现在是 Co-work 和 Claude Code 一堆使用场景的底层，那是增长团队推出来的。"我们当时有一个非常看好它的工程师，我们就说：没有人在做这件事，我们来做。"——这是他在任何其他公司都不会做的赌注。

我一开始想把这句话框成"时代变了、方法过期了"——传统增长那套 A/B、复利打磨在 AI 公司不灵了。但越想越觉得不对。Amol 说的根本不是方法对不对的问题，他说的是 **任务本身换了**。传统增长是在一片已经成熟的绿地里精耕细作，把每一棵植物的产量从 100 提升到 110；Anthropic 现在做的，是站在一片荒漠前面，做的事情是不断种出新的绿洲——比的是覆盖了多少新地，而不是单棵植物上挖多深。这两件事调用的，是完全不同的肌肉。我自己做 vibe coding 的过程其实也是这种感觉——做拾读、做 fcq.md、做小红书账号采集工具、给闲逛搭那一套 UGC 分析工作流，每一个项目都是在一片几乎没有人走过的小荒漠里种新东西。我没花太多时间在某个点击率上抠 5%，因为下一片可以种的地比我手头能优化的东西多得多。

## 那小优化到底交给谁

那如果大赌注是人类干的，每周还在跑的那一堆小优化谁去做？这是我听到一半时心里冒出来的问题。Anthropic 给了两个答案，都很硬。

第一个是把这层活儿喂给 Claude。他们内部有个项目叫 CASH（Claude Accelerates Sustainable Hypergrowth，Amol 自己说这名字有点 cringe），核心是把整条增长实验链路——识别机会、构建功能、跑测试、出洞察——切成四个可 eval、可 hill-climb 的环节，让 Claude 去打分、去推进。Amol 说目前的水平大约是一个工作两三年的初级 PM，比高级 PM 还差一档，但两个月前这件事根本不可能，是 Opus 4.5 之后才勉强能跑、Opus 4.6 才像样。他形容这件事像"按下播放键就开始印钱"——目前主要还是文案改动和一些小的 UI 微调，但已经在持续出结果。

第二个答案更有意思，也更反共识：把"工程师当 PM 用"。Anthropic 内部有一条非常具体的规则——**两周以内的工程量，工程师就是这个项目的 PM**，要自己去找法务、找安全、找跨部门对齐，PM 只在严重跑偏时介入；超过两周才轮到 PM 完整 own 起来。Amol 给这事的逻辑是：Claude Code 让工程师的产出至少翻了 2 到 3 倍，原来 5 个工程师的小组现在做的事情相当于 15 到 20 个工程师，PM 和设计的人数没变，于是被严重挤压了。他们没有按照流行叙事让 PM 去学写代码、学发 PR——而是反过来 deputize 那批"产品感强的工程师"做 mini PM，把 PM 自己腾出来去做更高杠杆的事。Amol 说得很直白：如果你只有 1 到 2 个 PM 对着 20 个工程师，你时间的边际价值不是去多 ship 一个 feature，而是把整支团队对"为什么做这件事、做什么"的判断质量再提 5%，那才是高杠杆。

更狠的是：他承认自己讨厌 PRD。"我们 ship 的东西里大概 70-80% 是没有 PRD 的。"小事直接在 Slack 里来回几条就开干；只有真正重大的事情才会做一份正经文档，但即使在那种场景里，他更看重的也是一个 30 分钟的跨部门 kickoff——把法务、安全、相关 stakeholder 拉到一个房间里，让大家一次性把要 care 的事说清楚，比写一份没人看的文档有用得多。这一段我笑了——因为这跟我自己 vibe coding 的工作流几乎是一样的：我做拾读的时候没写过任何 PRD，做 fcq.md 时也没有，连给闲逛搭工作流的时候都是直接对着 Claude Code 把脑子里的想法 vibe 成一版能跑的东西，跑通之后再回头补一句话的说明。我以前觉得这只是"独立做事的人偷懒"，听完这期才意识到，**这种"去文档化、直接动手"的工作模式，并不是因为我不专业，而是因为在 AI 把执行成本压到地板的世界里，它就是更高效的姿势**。Anthropic 内部那群人已经在按这个姿势跑了，区别只在于他们的执行链路上多了一群活的工程师做 mini PM，而我作为独立 vibe coder，"那群工程师"就是 Claude Code 自己。

## "好摩擦"这件事，AI 暂时学不会

这期最让我想停下来抄笔记的一段是关于摩擦。Amol 在 Mercury 时做过一个反直觉的实验：用一整个季度，不看任何指标、不看转化率、不看增长，只把银行类产品那条复杂的 onboarding 流程的"品质"做到极致。结果那是他职业生涯里增长影响力最大的一个季度——从开始到完成的转化率显著提升，**只是因为他们专注于品质本身**。后来在 Anthropic，他们的 onboarding 也是同一个思路：会主动问用户"你是谁、你的兴趣领域是什么"，然后用这些信息去推荐产品和功能。很多人看了直摇头说你们摩擦太重了，他说我们对它的表现相当满意。

他给了一个判断标准我特别认：摩擦真正要砍的不是"让用户慢一点"的步骤，而是那些"不能帮用户理解这个产品是不是为他准备的"的步骤；反过来，如果一个步骤能让用户更清楚"这东西就是给我用的"，哪怕它会让流程变长，也不该砍。Masterclass 的购买流程里有一个长长的兴趣测验，Calm 也有，Anthropic 也有——这些都不是设计失误，是经过严格测试的有效摩擦，是收入驱动因素。

> "当摩擦不能帮助用户理解这个产品是为我准备的时候，去掉它。但如果摩擦能帮助用户理解产品、找到最相关的使用方式——不要害怕它。"

听到这段我立刻想到拾读。我做拾读的时候纠结过同一件事：要不要让用户进来就直接刷内容，把所有问"你关心什么主题"的步骤砍掉？最快的版本是这样的，但我后来发现，**对一个付费内容产品，"省掉问问题"恰恰是把成本转嫁给了用户自己——他要在一堆陌生内容里自己找出哪些是给他的**。摩擦真正的作用不是拦截，而是匹配。这种判断 AI 暂时做不好，因为它需要的是"这个用户为什么会想用这个产品"的同理心，不是"哪种文案点击率高"的统计直觉。

---

整期播客里我笑出声的那个瞬间，是 Amol 和他们设计负责人 Joel 在一次艰难会议后的复盘。Joel 给他发消息：「Amol，就算我们有了 AGI，把六个人拉到一个房间里对齐意见，还是会是一件不可能的事。」这句话之所以好笑，是因为它精准地指出：AI 可以替代执行，可以替代分析，可以替代相当一部分判断，但短期内它替代不了"人类政治"。任何一个产品决策的瓶颈，最后往往不是技术、不是数据，而是几个人对优先级的扯皮。Amol 用一个词概括过这个问题——**capability overhang**：模型能力进步的速度已经远远超过产品侧能消化的速度，你刚为 Opus 4 设计完一套 onboarding 流程，下一代模型出来又把这套结论推翻了。这中间的差距，全要靠人去填。

而他自己填这个差距的方式我也很想抄。Amol 说他个人有一个 co-work 的 scheduled task 每天早上自动跑：扫 20-25 个图表、扫 Slack 找潜在的"跨部门错位"、把直接下属这一周的产出和团队 OKR 对一遍、甚至按他 manager Anvy Vora 公开写过的所有 PM 文章去模拟"如果是 Anvy，她这周会给我什么反馈"。他说这层东西还做得"像一个偶尔有点醉的教练"，但已经在每周帮他抓出几次会让团队空转的错位。这种"用一个 agent 持续在背后帮你看你看不过来的东西"的姿势，对独立 vibe coder 来说反而比对大公司更友好——因为我没有团队帮我 cover 盲区，所有的 dashboard 都只能我自己盯。

听完这期我没觉得自己应该立刻把所有方法翻一遍。只想到一件具体的事：下周开始，把我现在 80+ 个 skill 里跑得最频繁的那几个加一层 scheduled review，让 Claude 每周自己跑一遍、告诉我哪一个 skill 的输出在退化、哪一个值得加新的 case、哪一个应该被合并或者删掉。这件事跟"换一种工作方式"无关，只是我想知道，自己这个独立 vibe coder 的工作里，有哪一部分是可以彻底松开手的——交给 Claude 自己 hill climb，比我自己动手快得多。
